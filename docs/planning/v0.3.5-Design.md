## 0. Amendment note (2026-05-14) — the TensorEngine pivot

The original v0.3.5 design specified a **hybrid mathjs/TF.js numerical backend**. Two facts surfaced after the design was approved:

1. **TF.js has no float64 dtype.** `@tensorflow/tfjs` is float32-only (`DataTypeMap` = `float32 | int32 | bool | complex64 | string`). The design's ±10⁻⁹ BE-37 acceptance criterion and Decision 7's "TF.js float64" are unachievable in float32.
2. **mathjs was never a UPT dependency.** The design states three times (§2.2, §3, Decision 3) that "mathjs is already a UPT dependency." It is not — `package.json` has no `dependencies` block at all. The `'symbolic'` numerical-pderiv path (`mathjs.derivative()`) had no library behind it.

So *both* halves of the "hybrid" backend were phantom. The pivot, directed by the owner:

- **The compute layer becomes a `TensorEngine` interface** (the contract) with a **pure-TypeScript `Float64ReferenceEngine`** as v0.3.5's implementation — `Float64Array`-backed, naive contraction, **zero runtime dependencies**.
- **A souped-up MathTS rank-N tensor type** (`@danielsimonjr/mathts-tensor`, built in the `~/Dropbox/Github/Mathts` repo) becomes a **second** `TensorEngine` implementation, **interleaved into this same plan**, conformance-tested against the identical suite, and becomes UPT's *default* engine in v0.4.0 when grid-scale performance matters. v0.3.5 ships with the reference engine as default; UPT is never blocked on MathTS.
- The two repos develop **in parallel against one shared contract** — the parameterized `TensorEngine`-conformance test suite (§9) is that contract.

Consequences, applied throughout this document: Decision 4 (operand-contagion dispatch) and Decision 8 (`tf.tidy()`) are **deleted** — a single homogeneous engine has no cross-backend boundary and no manual memory management. Decision 12 changes: the TF.js *native* `optionalDependencies` (a compiled binary requiring runtime detection) is deleted; in its place `@danielsimonjr/mathts-tensor` — a **pure-JS** package — is an `optionalDependency`, so the zero-dependency `Float64ReferenceEngine` stays the default and `MathTSEngine` is genuinely opt-in. The three-way pderiv (Decision 5) becomes two-way. The two CRITICAL adversarial findings of §13 (backend contagion, return-tensor lifecycle) are **structurally eliminated**, not merely mitigated. The amended design is strictly smaller than the original.

## 1. Context

UPT v0.3.1 ([commit `da74737`, tag `v0.3.1`, 2026-05-13](https://github.com/danielsimonjr/universal-physics-tensor/releases/tag/v0.3.1)) closed the v0.3.x metric-layer line: `metric-tensor`, `kronecker-delta`, and `tensor-partial-derivative` AST nodes plus `raise()`/`lower()` helpers with internal alpha-conversion, then three audit-driven patch fixes. The catalog stands at 1,293 passing tests / 1,300 total (7 todo), 92 files. Everything in v0.3.x so far is **symbolic**: the validator inspects AST structure and infers dimensions, but nothing computes a concrete numerical value.

v0.3.5 adds the **numerical-contraction backend**: the machinery that takes a validated UPT AST plus concrete numerical inputs and produces actual numbers. This is the load-bearing validation of the v0.3.0 design — if there is a hidden schema issue in how `metric-tensor` or `tensor-partial-derivative` lowers to numerical operations, v0.3.5 surfaces it before v0.4.0 (Christoffel symbols + covariant derivative) builds on top.

The v0.2.0 symbolic layer already pre-cut the seam: `computeContraction()` in `src/dimensional/tensor.ts` returns `contractionPairs`, and its doc comment states the future numerical backend "will call `computeContraction` with the same operand list, pair the returned `contractionPairs` with its own einsum-pattern compiler, and multiply concrete numerical tensors." The `TensorEngine` interface drops directly into that published contract.

## 2. Scope

### In scope

1. **`src/numerical/` module**: new top-level module exposing `evaluateNumerical(node, inputs): Promise<NumericalResult>`, `evaluateNumericalRaw(...)`, `evaluateMetricInverse(...)`, and the AST→engine lowering pass. Parallel to `src/dimensional/` (analyzer) and `src/bridges/` (equations).
2. **`TensorEngine` interface + `Float64ReferenceEngine`**: the compute contract, plus a pure-TypeScript `Float64Array`-backed implementation. Zero runtime dependencies. Owns rank-N tensor construction, einsum/contraction, matMul, transpose, reshape, and elementwise ops.
3. **Souped-up MathTS rank-N tensor type** (`@danielsimonjr/mathts-tensor`, in the `~/Dropbox/Github/Mathts` repo): a second `TensorEngine` implementation, built and conformance-tested in this plan. Becomes UPT's default engine in v0.4.0.
4. **Two-way numerical partial derivative**: `tensor-symbol` gains an optional `numericalForm?: 'symbolic' | 'numerical-fn' | 'grid'` field. `∂_μ T` is computed via centered finite-difference over a `GridField` (`'grid'`) or finite-difference over a caller-supplied function (`'numerical-fn'`). `'symbolic'` is the AST default *value* (so every v0.3.0/v0.3.1 AST is a valid v0.3.5 AST) but, with no CAS in v0.3.5, a `'symbolic'`-tagged tensor-symbol appearing under a `tensor-partial-derivative` requires explicit derivative components supplied in `NumericalInputs`.
5. **`Violation.severity` field**: optional `severity?: 'error' | 'warning'` on the `Violation` interface, defaulting to `'error'`. Zero v0.3.0 migration cost.
6. **`InverseMetricInconsistencyWarning`**: deferred from v0.3.0 (Design §13 Q2). Fires at both `validate()` (symbolic structural check) and `evaluateNumerical()` (numerical `‖g⁻¹g − I‖` check). Deduplicated via hash.
7. **BE-37 numerical eikonal evaluator**: lower `BE37_EIKONAL_LHS` with concrete weak-field Schwarzschild components, numerically integrate the Shapiro delay Δt along a null ray, cross-check against the existing closed-form `evaluateShapiroDelay()` to ±10⁻⁹ relative error. End-to-end smoke test.
8. **API-stability pass**: extend `tests/bridges/public-api-stability.test.ts` to snapshot the v0.3.0 metric surface + the new `src/numerical/` surface; `@public` / `@internal` JSDoc tags on every export.

### Explicitly out of scope (deferred to later versions)

- **True autograd / reverse-mode AD**: the original design's `'tfjs-fn'` path was `tf.grad()` autograd. With no TF.js, v0.3.5 ships finite-difference (`'numerical-fn'`) instead. Reverse-mode AD is a v0.4.0+ concern (it is the natural enabler for the Christoffel term).
- **MathTS as UPT's default engine**: v0.3.5 ships `Float64ReferenceEngine` as default. The `MathTSEngine` is built and conformance-green in v0.3.5 but becomes default in v0.4.0.
- **Browser float32 / precision-mode toggle**: the `TensorEngine` interface makes a float32 engine just another implementation. The `setPrecision()` knob is v0.5.0+ threejs-visualization work.
- **Christoffel symbols, covariant derivative**: v0.4.0 ("connection layer").
- **Riemann / Ricci / Bianchi curvature, Einstein field-equation solvers**: v0.5.0+.
- **Contraction-path optimization** (NP-hard einsum ordering): v0.3.5 ships naive left-to-right contraction order. Path optimization is a v0.4.0+ performance concern.
- **GPU / WebGL / WASM backend**: a v0.5.0+ performance concern — another `TensorEngine` implementation.
- **Grid-scale PDE solving** (BSSN formalism): v0.5.0+. v0.3.5's `'grid'` `numericalForm` ships the `GridField` data structure and finite-difference `∂_μ`, but not time-evolution solvers.

## 3. Approach: one interface, one reference engine, a second engine in parallel

The pattern adopted from v0.3.0 holds: minimal, well-bounded units; spec the contract; test in layers. The architectural surface, post-pivot:

- **One compute contract.** `TensorEngine` is an interface (`src/numerical/tensor-engine.ts`) defining rank-N tensor construction, einsum/contraction, matMul, transpose, reshape, elementwise add/sub/scale/mul, identity, and norm — everything the AST lowering pass needs. `EngineTensor` is the opaque tensor handle the interface trades in.
- **One reference implementation, shipping in v0.3.5.** `Float64ReferenceEngine` (`src/numerical/float64-engine.ts`) is pure TypeScript, `Float64Array`-backed, row-major with strides, naive O(n) contraction. Adequate for v0.3.5's scope (4×4 Schwarzschild metrics). Zero runtime dependencies — UPT installs nothing new.
- **A second implementation, built in parallel.** `MathTSEngine` (`src/numerical/mathts-engine.ts`) is a thin adapter wrapping `@danielsimonjr/mathts-tensor` — the rank-N tensor type added to the MathTS repo in this same plan. It is conformance-tested against the *identical* suite as the reference engine. The two repos develop concurrently against the `TensorEngine` contract; neither blocks the other.
- **No cross-backend dispatch.** The original design's operand-contagion dispatch (Decision 4) existed to route sub-expressions between mathjs and TF.js. With one homogeneous engine, the lowering pass simply walks the AST and emits `TensorEngine` calls — no per-operand backend tagging, no contagion rules.
- **Async surface, synchronous core.** `evaluateNumerical()` is `async` — a forward-compat hedge so a future worker/GPU engine can be async without an API break. The `Float64ReferenceEngine` and `MathTSEngine` are both synchronous pure-JS; the async wrapper simply `await`s nothing meaningful in v0.3.5. (Decision 6 — kept in shape, no longer *forced* by TF.js Promises.)
- **GC-managed memory.** Pure-JS engines produce GC-managed tensors. No `tf.tidy()`, no `.dispose()` discipline. `evaluateNumericalRaw()` still exists for chaining workloads (it returns the live `EngineTensor` instead of extracting to plain JS), and `NumericalRawResult.dispose()` is retained on the interface as an optional no-op so a future native engine can implement real disposal — but for v0.3.5's engines it does nothing.

## 4. AST extension

### Existing node types (v0.3.1, unchanged shapes)

The numerical backend reads validated v0.3.1 ASTs. No node *shapes* change in v0.3.5 except one additive optional field on `TensorSymbolNode`:

```typescript
// src/dimensional/tensor.ts — TensorSymbolNode gains one optional field
export interface TensorSymbolNode {
  readonly kind: 'tensor-symbol';
  readonly name: string;
  readonly indices: ReadonlyArray<TensorIndex>;
  readonly dim: Dimension;
  readonly role?: Role;
  readonly numericalForm?: 'symbolic' | 'numerical-fn' | 'grid';  // NEW in v0.3.5; defaults 'symbolic'
}
```

`numericalForm` defaults to `'symbolic'` when omitted — so every v0.3.0/v0.3.1 AST is a valid v0.3.5 AST with no change. The field tells the numerical pderiv dispatcher (§6) which differentiation strategy to use for that tensor-symbol when it appears as the `of` operand of a `tensor-partial-derivative`.

### `Violation` interface extension (`src/dimensional/validator.ts`)

```typescript
export interface Violation {
  location: string;
  expected: Dimension;
  actual: Dimension;
  note: string;
  severity?: 'error' | 'warning';   // NEW in v0.3.5; absent ⇒ 'error'
}
```

`ValidationResult.ok` becomes: `ok = !violations.some(v => (v.severity ?? 'error') === 'error') && dim !== null`. Warnings do not fail validation. All v0.3.0/v0.3.1 violation-construction sites omit `severity`, so they are treated as `'error'` exactly as before — zero behavior change for the existing suite.

## 5. `src/numerical/` module architecture

### File structure

```

  tensor-engine.ts        — the TensorEngine interface + EngineTensor handle type.
```

### `TensorEngine` interface (`src/numerical/tensor-engine.ts`)

```typescript
/** Opaque rank-N tensor handle. Each engine defines its own concrete type;
 *  consumers treat it as opaque and only operate on it through TensorEngine. */
export interface EngineTensor {
  readonly shape: ReadonlyArray<number>;
}

/** The compute contract. Float64ReferenceEngine and MathTSEngine both implement it. */
export interface TensorEngine {
  readonly name: string;

  /** Build a tensor from nested-array (or scalar) data + an explicit shape. */
  fromNested(data: number | NestedArray, shape: ReadonlyArray<number>): EngineTensor;
  /** Extract to plain JS: a number for rank-0, nested arrays for rank ≥ 1. */
  toNested(t: EngineTensor): number | NestedArray;

  /** Einstein contraction driven by an einsum spec. `spec` pairs operand axes
   *  to contract (built by lowering.ts from computeContraction's contractionPairs)
   *  and lists the surviving free axes in output order. */
  einsum(spec: EinsumSpec, ...operands: EngineTensor[]): EngineTensor;
  matMul(a: EngineTensor, b: EngineTensor): EngineTensor;
  transpose(t: EngineTensor, perm?: ReadonlyArray<number>): EngineTensor;
  reshape(t: EngineTensor, shape: ReadonlyArray<number>): EngineTensor;

  add(a: EngineTensor, b: EngineTensor): EngineTensor;
  sub(a: EngineTensor, b: EngineTensor): EngineTensor;
  mul(a: EngineTensor, b: EngineTensor): EngineTensor;       // elementwise (Hadamard)
  scale(t: EngineTensor, k: number): EngineTensor;

  identity(n: number): EngineTensor;                          // n×n
  /** ∞-norm of the flattened tensor — used by the inverse-metric check. */
  normInf(t: EngineTensor): number;

  /** Optional no-op for pure-JS engines; a future native engine implements
   *  real disposal. evaluateNumerical() never relies on it. */
  dispose?(t: EngineTensor): void;
}
```

`EinsumSpec` (also in `tensor-engine.ts`) is the lowering-pass→engine handoff: `{ contractions: Array<{ pair: [[operandIndex, axis], [operandIndex, axis]] }>, free: Array<{ operand, axis }> }` — the contracted index pairs plus the ordered surviving free axes. It is engine-agnostic — `Float64ReferenceEngine` interprets it with nested loops; `MathTSEngine` translates it to a MathTS einsum/contraction call. **`lowering.ts` does NOT decide which indices contract** — it calls `computeContraction()` (the v0.2.0 symbolic-layer authority, which is variance-aware and applies the implicit-identity-metric rule) to get `contractionPairs` + `freeIndices`, then maps those labels to `(operand, axis)` sites. There is exactly one contraction-decision implementation in the codebase.

### Public surface (`src/numerical/index.ts`)

```typescript
/** Plain-JS numerical result. `value` is a number for rank-0, nested arrays for rank ≥1. */
export interface NumericalResult {
  readonly value: number | NestedArray;
  readonly dim: Dimension;
  readonly freeIndices: ReadonlyMap<string, { upper: number; lower: number }>;
  readonly warnings: ReadonlyArray<Violation>;   // severity === 'warning' violations
}

/** Live-EngineTensor result for chaining workloads (geodesic integration, BSSN). */
export interface NumericalRawResult {
  readonly value: EngineTensor;
  readonly dim: Dimension;
  readonly freeIndices: ReadonlyMap<string, { upper: number; lower: number }>;
  readonly warnings: ReadonlyArray<Violation>;
  dispose(): void;        // no-op for v0.3.5 pure-JS engines; kept for forward-compat
}

export interface EvaluateOptions {
  /** Engine override. Defaults to the registry's active engine
   *  (Float64ReferenceEngine in v0.3.5). */
  readonly engine?: TensorEngine;
}

/** Evaluate a validated AST to plain JS. */
export function evaluateNumerical(
  node: ExprNode,
  inputs: NumericalInputs,
  options?: EvaluateOptions,
): Promise<NumericalResult>;

/** Evaluate to a live EngineTensor for chaining. */
export function evaluateNumericalRaw(
  node: ExprNode,
  inputs: NumericalInputs,
  options?: EvaluateOptions,
): Promise<NumericalRawResult>;

/** Numerically check g⁻¹g ≈ I. Returns the residual norm + a warning-severity
 *  Violation if it exceeds tolerance. */
export function evaluateMetricInverse(
  g: MetricTensorNode,
  gInverse: MetricTensorNode,
  inputs: NumericalInputs,
  tolerance?: number,               // default 1e-10 in float64
  options?: EvaluateOptions,

```

### `NumericalInputs` shape

```typescript
export interface NumericalInputs {
  /** Concrete component values for each tensor-symbol / metric-tensor by name.
   *  Shape must match the node's rank + index dimensionality. */
  readonly tensors: ReadonlyMap<string, NestedArray | number>;
  /** For 'numerical-fn' numericalForm tensor-symbols: a function
   *  (coords: ReadonlyArray<number>) => number | NestedArray. Differentiated
   *  by centered finite-difference. */
  readonly fields?: ReadonlyMap<string, (coords: ReadonlyArray<number>) => number | NestedArray>;
  /** For 'grid' numericalForm tensor-symbols. */
  readonly grids?: ReadonlyMap<string, GridField>;
  /** For 'symbolic' numericalForm tensor-symbols appearing under a
   *  tensor-partial-derivative: explicit pre-computed derivative components,
   *  keyed by `${symbolName}/${coordLabel}`. (v0.3.5 has no CAS — see §6.) */
  readonly derivatives?: ReadonlyMap<string, NestedArray | number>;
  /** Coordinate values for partial-derivative evaluation. */
  readonly coords?: ReadonlyMap<string, number>;
}
```

### `GridField` (`src/numerical/grid-field.ts`)

```typescript
export interface GridField {
  /** Per-axis sample count, e.g. [64, 64, 64] for a 3D spatial grid. */
  readonly shape: ReadonlyArray<number>;
  /** Per-axis physical spacing Δx for the finite-difference stencil. */
  readonly spacing: ReadonlyArray<number>;
  /** The sampled field values as a nested array of `shape`. */
  readonly data: NestedArray;
  /** Boundary policy for stencils at the grid edge. v0.3.5 ships 'clamp' and
   *  'periodic'; 'ghost' (ghost-cell padding for BSSN-style PDE solvers) is
   *  deferred to v0.5.0. */
  readonly boundary: 'clamp' | 'periodic';
}
```

## 6. Numerical partial-derivative dispatch (`src/numerical/pderiv.ts`)

When the lowering pass hits a `tensor-partial-derivative` node, it reads the `of` operand's `numericalForm` (defaulting `'symbolic'`):

| `numericalForm` | Strategy | Mechanism | Notes |
|---|---|---|---|
| `'grid'` | Centered finite-difference | O(h²) stencil over the `GridField`, step from `GridField.spacing`, edges per `GridField.boundary` | The primary working differentiation path in v0.3.5. |
| `'numerical-fn'` | Centered finite-difference on a supplied function | O(h²) stencil; `h` is a small fraction of the coordinate scale (default `1e-6 · max(|x|, 1)`) | Replaces the original design's `tf.grad()` autograd path. Not machine-precision — finite-difference truncation error applies. |
| `'symbolic'` | No CAS in v0.3.5 | The lowering pass looks up `inputs.derivatives.get('${name}/${coordLabel}')`; if absent it throws `NumericalBackendError` with a clear message | The AST default. Every v0.3.0/v0.3.1 AST carries `'symbolic'` implicitly, but those ASTs do not appear *under a pderiv* in normal use; when they do, the caller supplies the derivative. True symbolic differentiation is a v0.4.0+ concern. |

The pderiv module stays small: it reads `numericalForm`, routes to one of three code paths, and returns an `EngineTensor` (built via the active engine's `fromNested`).

## 7. `InverseMetricInconsistencyWarning` (`src/numerical/` + `src/dimensional/validator.ts`)

Fires at **two** points (Decision 10):

- **Symbolic — opt-in via `validateInverseMetricPair(gLower, gUpper)`**: a standalone exported helper (not folded into `validate()` — `validate()` is the hot path for the 1,293-test suite and walking every AST for metric pairs there is unwarranted). Given an explicit lower/upper metric pair, it checks the structural shape (both-lower + both-upper, rank-2) and returns a `severity: 'warning'` `Violation[]` (deduplicated — at most one warning).
- **Numerical — fires automatically inside `evaluateNumerical()`**: `evaluateNumerical()` scans the AST for an identifiable lower/upper `metric-tensor` pair (cheap — it already walks the tree to lower it). When found, it builds both metrics as `EngineTensor`s, computes `engine.normInf(engine.sub(engine.matMul(gInverse, g), engine.identity(N)))`, and if it exceeds tolerance (default `1e-10` in float64) adds a `severity: 'warning'` `Violation` to `NumericalResult.warnings`. `evaluateMetricInverse()` exposes the same numerical check directly for callers who already hold the pair.

**Deduplication**: numerical warnings are keyed on `(gInverse.name, g.name)` and emitted at most once per `evaluateNumerical()` call.

## 8. BE-37 numerical eikonal evaluator (`src/numerical/null-ray-integrator.ts` + `src/bridges/equations/be-37-shapiro-delay.ts`)

The end-to-end smoke test. Steps:

1. Lower `BE37_EIKONAL_LHS` (`g^μν (∂_μ S)(∂_ν S)`) with concrete **weak-field Schwarzschild** `g^μν` components supplied via `NumericalInputs`, evaluated through the active `TensorEngine`.
2. Integrate the Shapiro delay Δt along a null ray using the **RK4 affine-parameterized null-geodesic integrator** (`null-ray-integrator.ts`). Fixed-step RK4; step count chosen so the cross-check below holds.
3. Cross-check the integrated Δt against the existing closed-form `evaluateShapiroDelay()` (the v0.3.0 scalar form, retained for exactly this purpose).

**Acceptance criterion:** integrated Δt agrees with closed-form `evaluateShapiroDelay()` to **±10⁻⁹ relative error** — comfortable in float64, well inside the ~10⁻⁵ Cassini experimental precision the bridge is grounded in.

The null-ray integrator is a genuine piece of implementation work — it gets its own task, not folded into a lowering task.

## 13. Risks and open questions

### Risks

- **Two-repo coordination (the pivot's main new risk).** The MathTS rank-N work happens in a separate repo. Mitigation: the parameterized `engine-conformance` suite (§9) is the contract — both engines run it. If the MathTS soup-up slips, **v0.3.5 still ships on `Float64ReferenceEngine`** (Tasks #6, #8, #11 are the only MathTS-dependent tasks; #11 can be deferred to a v0.3.6 patch without blocking the release). UPT is genuinely never blocked on MathTS.
- **MathTS repo maturity.** The MathTS repo carries ~700 dormant type errors in its `functions/` package (strict mode disabled there). The new `@danielsimonjr/mathts-tensor` package must be **strict-clean in its own right** — it does not inherit the `functions/` relaxation. Verified during Task #6 scaffold.
- **Null-ray integrator scope.** The BE-37 acceptance criterion requires a real null-geodesic integrator. Locked as RK4 affine-parameterized (§8), its own task (#13). If the ±10⁻⁹ criterion proves hard to hit at reasonable step counts, the fallback is to relax to ±10⁻⁷ (still inside Cassini precision) — but only with an explicit CHANGELOG note.
- **Naive contraction performance.** `Float64ReferenceEngine`'s O(n) nested-loop contraction is fine for 4×4 metrics but will not scale. This is by design — `MathTSEngine` (and later a GPU engine) is the performance answer. Flagged so v0.4.0 knows the reference engine is a correctness baseline, not a perf target.

### Eliminated risks (were CRITICAL in the original design)

- **Backend contagion** — *eliminated.* There is no mathjs/TF.js boundary; one homogeneous engine has nothing to contaminate.
- **Return-tensor lifecycle** — *eliminated.* Pure-JS engines produce GC-managed tensors; no `tf.tidy()` / `.dispose()` discipline to get wrong.
- **mathjs↔TF.js ArrayBuffer churn** — *eliminated.* No cross-engine boundary.
- **Precision boundary** — *eliminated.* Single float64 engine; no float32/float64 cliff. (Reappears at v0.5.0 with the browser float32 engine — out of scope here.)

### Open questions for written-spec review

1. **`evaluateMetricInverse` tolerance default.** §5 sets `1e-10` in float64. A fixed `1e-10` is the v0.3.5 baseline; whether it should scale with the metric's condition number is a v0.4.0 refinement.
2. **`EinsumSpec` shape.** §5 sketches it as contract-pairs + ordered free axes. The exact shape is locked in the implementation plan's Task #1 — both engines and `lowering.ts` depend on it, so it is the single most important interface decision in the plan.
3. **`'numerical-fn'` finite-difference step.** §6 defaults `h = 1e-6 · max(|x|, 1)`. Implementer confirms during Task #10; the BE-37 worked example does not use this path (it is `'symbolic'` with explicit/integrator-supplied derivatives), so the default is not load-bearing for the release criterion.
4. **Naive contraction order.** v0.3.5 ships left-to-right einsum contraction (no path optimization), in both engines. Fine for 4×4 Schwarzschild metrics; flagged so v0.4.0 knows path optimization is unstarted.

## 14. Forward-compatibility sanity checks

### 14.1 `numericalForm` field is additive
`tensor-symbol` gains `numericalForm?` as an optional field defaulting to `'symbolic'`. Every v0.3.0/v0.3.1 AST is a valid v0.3.5 AST unchanged. JSON round-trip: a plain string — survives serialization trivially. Covered by Task #3.

### 14.2 `Violation.severity` field is additive
Optional field defaulting to `'error'`. All v0.3.0/v0.3.1 violation-construction sites are untouched; `ValidationResult.ok` semantics preserved for error-only violation sets. SemVer MINOR.

### 14.3 v0.4.0 covariant-derivative numerical composition
The original design leaned on `tf.grad()` autograd for v0.4.0's covariant derivative `∇_μ V^ν = ∂_μ V^ν + Γ^ν_μλ V^λ`. With autograd deferred (§2 out-of-scope), v0.4.0 has two routes: (a) finite-difference the Christoffel term via the `'grid'` / `'numerical-fn'` paths, or (b) add reverse-mode AD as a v0.4.0 capability of the `TensorEngine` interface (a new optional method). The `TensorEngine` interface is the right place for it — an engine that supports AD advertises it; one that does not falls back to finite-difference. v0.3.5 does not preclude either route.

### 14.4 v0.5.0 Faraday-cascade compatibility
The Faraday mixed-component-dim BREAKING refactor (Part-VIII §VIII.10) touches `metric-tensor.dim` / `tensor-symbol.dim` / `kronecker-delta.dim`. The numerical backend reads `dim` for the result's `NumericalResult.dim` field but does not branch on it for compute — so the v0.5.0 `dim`-shape refactor is contained to the symbolic layer; the numerical module's lowering logic is unaffected.

### 14.5 The `TensorEngine` interface is the v0.5.0 multi-engine seam
The original §14.5 (TF.js type-import isolation) is **deleted** — there is no TF.js. Its replacement concern: the `TensorEngine` interface must be expressive enough that a float32 browser engine, a WASM engine, and a GPU engine are all *just implementations*. The v0.3.5 interface is deliberately minimal (construction, einsum, the handful of ops the lowering pass needs) — a new engine implements exactly that surface. The `EngineTensor` handle is opaque, so engines are free to back it with `Float64Array`, a WASM linear-memory offset, or a GPU buffer handle.

### 14.6 Browser float32 forward-compat
v0.3.5 pins float64 (`Float64ReferenceEngine`). The v0.5.0 browser-portable float32 mode is a new `TensorEngine` implementation selected via `engine-registry.ts` / the `EvaluateOptions.engine` override — a localized addition, not a cross-cutting refactor. No v0.3.5 design decision precludes it.
