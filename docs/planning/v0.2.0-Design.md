## 1. Context

UPT v0.1.0 ([commit `b1eeff6`, tag `v0.1.0`, 2026-05-12](https://github.com/danielsimonjr/universal-physics-tensor/releases/tag/v0.1.0)) closed the Wave A → Wave Z arc with **40 / 40 AST encodings**, 1,161 tests, status distribution 6/31/3/0 (established / speculative / highly-speculative / invalid). The scalar-AST scope is exhausted; further encoding rigor requires extending the AST grammar.

The validator's source (`src/dimensional/validator.ts:5-6`) explicitly notes the v0.1.0 gap:

> "This MVP does NOT track tensor index structure (rank, contractions). Bridge Eq 17's index-rank mismatch from the spec cannot be caught here. Tier 4.5 follow-up — see README."

Bridges with tensor structure are currently encoded via the **typed-stub idiom**: a single symbol named `T_torsion_squared` whose `dim` is the hand-computed dimension of the contracted scalar `T_λμν T^λμν`. Honest about the limitation (every typed-stub is flagged in `notes`), but loses the index structure entirely. The validator cannot verify that the contraction is well-formed; it can only verify that the hand-computed dimension matches the expected result.

v0.2.0 adds the **algebra layer of Riemannian geometry**: variance-typed index labels and the Einstein summation contraction rule. Metric, raise/lower, covariant derivative, and curvature are explicitly deferred to v0.3.0+.

## 2. Scope

### In scope

1. **Spec module**: `docs/specification/Part-VII-Tensor-Algebra.md`. Defines the grammar, contraction rules, dimensional bookkeeping rules, and v0.2.0 limitations. Drift-tested against the implementation. **Includes a "partial-derivative preview" section** locking in the AST shape `{ kind: 'tensor-partial-derivative', wrtIndex: { label, variance: 'lower' }, of: ExprNode }` for v0.3.0 implementation (no v0.2.0 runtime support).
2. **AST extension**: two new node types — `tensor-symbol` (a tensor with named, variance-typed indices, **plus optional `role: 'coordinate' | 'field' | 'constant'` field defaulting to `'field'`** for the v0.3.0 partial-derivative work) and `tensor-product` (the Einstein-summation product, contracting all matching upper/lower pairs across operands).
3. **Validator extension**: enriched `ValidationResult` with a `freeIndices` map; recursive walker for the new nodes; strict-boundary rules for how `op` interacts with tensor operands; new error types (`IndexLabelCollisionError`, `VarianceMismatchError`, `RepeatedDummyLabelError`, `TensorInScalarOpError`).
4. **`UPTError` base class refactor**: introduce `class UPTError extends Error` in `src/dimensional/errors.ts` (or similar). Reparent existing `DimensionMismatchError` and all new v0.2.0 error types under it. Enables `error instanceof UPTError` discrimination by downstream consumers (mathjs, threejs, TensorJS). Small surface change, durable interop payoff. *(Adopted from §14.7 adversarial-review recommendation.)*
5. **Drift guard**: `tests/dimensional/tensor-spec-vs-impl.test.ts`, analog to existing `spec-vs-index.test.ts`. Every TENSOR-RULE marker in the spec has a matching implementation test; both directions enforced.
6. **AST → JSON serialization round-trip test**: `tests/dimensional/tensor-ast-serialization.test.ts`. Verifies a tensor AST can be serialized to JSON and reconstructed losslessly. Forward-compat for mathjs integration in v0.3.5. *(Adopted from §14.6 adversarial-review recommendation.)*
7. **Per-bridge structural rewrites**: BE-17 (remove `T_torsion_squared` stub), plus structural encoding for BE-33 (TeVeS tensor invariants), BE-36 (Bekenstein-Hawking on ER bridge), and BE-43 (Wheeler-Feynman EM tensor). The owner may keep one or two as stubs if literature gaps make structural encoding premature — honest-claude posture preserved.
8. **R4 polish**: 16 bridges with prose-only concerns in `notes` get structured `KnownIssue[]` arrays.
9. **Doc refresh**: `Bridge-Remediation-Plan.md`, `Development-Plan.md`, `Implementation-Plan.md` updated to reflect the post-Wave-Z state (no claims of "2 invalid"; "40 / 40 encoded" everywhere relevant).

### Explicitly out of scope (deferred to v0.3.0+)

- **Metric tensor** `g_μν`, `g^μν` — deferred to v0.3.0 (the "metric layer")
- **Raise/lower** `T^μ_ν = g_νλ T^μλ` — deferred to v0.3.0
- **Covariant derivative** `∇_μ` — deferred to v0.3.0 or v0.4.0 (the "connection layer")
- **Curvature tensors** Riemann, Ricci, scalar, Bianchi identities — deferred to v0.4.0+ (the "curvature layer")
- **Tensor-with-component-dependent-dimensions** (e.g., Faraday `F_μν` mixing electric and magnetic components with different SI dimensions). v0.2.0 assumes uniform component dimension per tensor-symbol; the spec documents this as a known limitation revisited with the metric.
- **Tensor-valued integrals/derivatives** — `integral` and `derivative` AST nodes remain scalar-only
- **Tensor exponentiation** `T^2` (ambiguous in physics literature; explicit contraction required)
- **Property-based testing** as a new paradigm (existing 1,161 deterministic tests are sufficient; revisit for v0.3.0 metric layer)
- **npm publish prep**, examples directory, contributor guide — deferred to a later release once API stabilizes through use

## 3. Approach: spec-first, minimal runtime

**Both reasoning models converged on the same verdict with high confidence:** spec-first methodology (matching UPT's existing pattern in Part-I through Part-VI) with the minimal-AST implementation. Specifically:

1. Write `Part-VII-Tensor-Algebra.md` first. Define the grammar formally. Define the contraction rules. Document the v0.2.0 limitations (uniform component dimension, no metric, etc.).
2. Implement the minimal runtime AST extension matching the spec.
3. Add a drift guard that enforces non-divergence in both directions.

**Rejected alternative**: type-level encoding via TypeScript conditional types and template literal types (`TensorExpr<['μ','ν'], ['α','β']>`). Both reasoners called this "a siren song" for a single-developer library — significant complexity, slow compile times, marginal benefit given the existing test coverage. The structural rigor lives in the runtime validator; TypeScript types stay simple.

**Gemini's clarifying principle, adopted:** *"The primary consumer of the raw AST is the system itself, not the end-user."* The AST stays minimal and structurally precise; user-facing ergonomics (e.g., `scale(scalar, tensor)`) live in a thin API helper layer that constructs the underlying nodes.

## 4. AST extension

### Existing node types (v0.1.0, unchanged)

```typescript
| { kind: 'symbol'; name: string; dim: Dimension }
| { kind: 'op'; op: '+'|'-'|'*'|'/'|'^'; args: ExprNode[] }
| { kind: 'integral'; over: ExprNode; integrand: ExprNode }
| { kind: 'derivative'; of: ExprNode; wrt: ExprNode }
```

### New node types (v0.2.0)

```typescript
| { kind: 'tensor-symbol';
    name: string;
    indices: ReadonlyArray<{ label: string; variance: 'upper' | 'lower' }>;
    dim: Dimension }
| { kind: 'tensor-product'; args: ExprNode[] }
```

**`tensor-symbol`** represents a named tensor with explicit indices. The `dim` field is the **per-component dimension** — every component is assumed to share this dimension (v0.2.0 limitation; see § Non-goals). Indices appear in declaration order; the validator does not reorder them. Repeated labels within a single `tensor-symbol`'s indices array are rejected at validation time.

**`tensor-product`** represents the generalized Einstein-summation product. The validator:

1. Recursively validates each `args[i]`, obtaining `{ dim_i, freeIndices_i }`.
2. Multiplies the dimensions: `dim = multiply(multiply(... dim_0, dim_1) ...)`.
3. Unions the `freeIndices` maps (summing the `upper` and `lower` counts per label across all args).
4. For each label where both `upper > 0` and `lower > 0`, performs Einstein contraction: decrements both counts by `min(upper, lower)`.
5. Rejects any label whose total post-contraction count exceeds 2 (label collision; the user must rename one of the indices).

The result of `tensor-product` is a `{ dim, freeIndices }` pair. If `freeIndices` ends up empty (all indices contracted away), the result is a scalar and can slot directly into `op '+'`, `op '*'`, etc.

## 5. Validator architecture

### Enriched `ValidationResult`

```typescript
export interface ValidationResult {
  ok: boolean;
  inferredDimension: Dimension | null;
  freeIndices: Map<string, { upper: number; lower: number }>;  // NEW
  violations: Violation[];
}
```

**`freeIndices` invariants:**
- For a scalar expression: empty map (or absent entries).
- For a tensor expression with k free indices: each label has exactly one non-zero count (either `upper: 1, lower: 0` or `upper: 0, lower: 1`). Total non-zero entries = k.
- An invalid construct like `T^μ_μ_μ` (label used three times in one tensor-symbol) is rejected with `RepeatedDummyLabelError` before contraction.

### Per-node validation rules

| Node kind | Free-indices rule | Dim rule | Errors raised |
|---|---|---|---|
| `symbol` | Always empty | `node.dim` | — |
| `tensor-symbol` | Built from `node.indices`; reject if any label repeats | `node.dim` | `RepeatedDummyLabelError` |
| `op '+' / '-'` | All args must share same map | All args must share same dim | `DimensionMismatchError`, `FreeIndexMismatchError` |
| `op '*' / '/'` | All args MUST have empty map | Multiply / divide | `TensorInScalarOpError` |
| `op '^'` | Base must have empty map; exponent must be DIMENSIONLESS scalar | `power(base.dim, exponent.value)` | `TensorInScalarOpError`, `NonScalarExponentError` |
| `integral` | Integrand must have empty map (scalar-only in v0.2.0) | `multiply(integrand.dim, over.dim)` | `TensorIntegralError` (deferred feature) |
| `derivative` | Both sides must have empty map (scalar-only) | `divide(of.dim, wrt.dim)` | `TensorDerivativeError` (deferred feature) |
| `tensor-product` | Union args' maps; contract matching pairs; reject label collisions (count > 2) | Multiply args' dims | `IndexLabelCollisionError`, `VarianceMismatchError` |

### Strict-boundary rationale

The boundary `op` is strictly scalar / `tensor-product` is the only multiplicative path for tensors was confirmed by both reasoners. Auto-promoting `op '*'` to tensor-aware behavior would introduce semantic ambiguity at the core of the AST. The cost — slightly more verbose AST construction for scalar-times-tensor expressions — is absorbed by helper functions in the user-facing API layer.

## 6. User-facing API

```typescript
// src/dimensional/tensor.ts

/** Construct a tensor symbol. */
export function tsym(
  name: string,
  indices: ReadonlyArray<{ label: string; variance: 'upper' | 'lower' }>,
  dim: Dimension
): ExprNode;

/** Scale a tensor by a scalar coefficient. Returns a tensor-product. */
export function scale(scalar: ExprNode, tensor: ExprNode): ExprNode;

/** Contract any number of tensors. Returns a tensor-product. */
export function contract(...tensors: ExprNode[]): ExprNode;

/** Construct a tensor sum (uses op '+' with strict free-index matching). */
export function tsum(...tensors: ExprNode[]): ExprNode;
```

These are sugar for AST construction; the validator sees only the underlying nodes. The helpers exist in `src/dimensional/tensor.ts` so bridge encoders can import them alongside the scalar helpers (`sym`, `op`) from the existing modules.

## 7. Worked example: BE-17 before / after

### Before (v0.1.0 typed-stub)

```typescript
// S²_spin = (c⁴/(8πG))² · T_torsion_squared
const T_torsion_squared = sym('T_torsion_squared',
  { L: -4, M: 0, T: 2, I: 0, Theta: 0, N: 0, J: 0 }); // hand-computed

const BE17_RHS = {
  kind: 'op', op: '*',
  args: [coupling_prefactor_squared, T_torsion_squared],
};
```

The validator infers dim `[M²·L⁻²·T⁻²]` but never sees that the stub represents `T_λμν T^λμν` — the rank, contraction pairs, and variance structure are all opaque.

### After (v0.2.0 structural)

```typescript
const T_lower = tsym('T_torsion',
  [{ label: 'λ', variance: 'lower' },
   { label: 'μ', variance: 'lower' },
   { label: 'ν', variance: 'lower' }],
  { L: -2, M: 0, T: 1, I: 0, Theta: 0, N: 0, J: 0 }); // component dim

const T_upper = tsym('T_torsion',
  [{ label: 'λ', variance: 'upper' },
   { label: 'μ', variance: 'upper' },
   { label: 'ν', variance: 'upper' }],
  { L: -2, M: 0, T: 1, I: 0, Theta: 0, N: 0, J: 0 });

const T_contracted = contract(T_lower, T_upper);
// validator: dim=[T²·L⁻⁴], freeIndices=empty (λ, μ, ν all contracted)

const BE17_RHS = contract(coupling_prefactor_squared, T_contracted);
// validator: dim=[M²·L⁻²·T⁻²], freeIndices=empty
```

The validator now **structurally verifies**:
- Three matching upper/lower pairs (λ, μ, ν all dummy)
- Final expression has empty `freeIndices` (true scalar)
- Component dimension composes to `[T²·L⁻⁴]` for the contraction
- Multiplying by `[M²·L²·T⁻⁴]` coupling yields `[M²·L⁻²·T⁻²]` ✓

The `T_torsion_squared` typed-stub disappears. The encoding matches the literature's tensor structure directly. If a future spec edit mis-pairs the indices (say, accidentally puts μ as upper in both factors), the validator catches it; the v0.1.0 stub couldn't.

### Drift guard mechanism

Part-VII embeds structured markers:

```markdown
<!-- TENSOR-RULE: op-star-rejects-tensors -->
The validator rejects `op '*'` with any argument whose freeIndices map is non-empty,
emitting `TensorInScalarOpError`.
```

The test parses Part-VII, extracts every `<!-- TENSOR-RULE: <id> -->` marker, and asserts:
- Every rule marker has a matching test (test name or test-id metadata references the rule).
- Every test that claims a rule reference points to a real rule marker.
- The test for each rule actually exercises the documented behavior (positive + negative cases).

A rule added to the spec without a test → fail. A test referencing a non-existent rule → fail.

### Performance

Validator recursion is O(N · F²) for tensor expressions, where N is node count and F is free-index count per subtree (≤ 4 in physics, usually 1-2). With pessimistic constants this stays well under the 23.6 s wall-clock budget the existing 1,161 tests consume. Re-benchmark at end of v0.2.0; flag any single test exceeding 100 ms.

## 12. North-star architecture: TensorJS

The end-state vision is **TensorJS**: a TypeScript physics-simulation engine for scientific inquiry, built as three composing layers:

```
│  │      UPT         │  │      mathjs      │  │     threejs      │   │
│  │  (this repo)     │  │  (external dep)  │  │  (external dep)  │   │
│  │                  │  │                  │  │                  │   │
│  │  Structural      │  │  Numerical       │  │  Interactive     │   │
│  │  correctness:    │  │  evaluation:     │  │  visualization:  │   │
│  │  - 40 bridge     │  │  - Matrix /      │  │  - 6D tensor     │   │

│                      ▼  ▼         ▼                                 │
│                  TensorJS public API: simulate(bridge, inputs)      │
└─────────────────────────────────────────────────────────────────────┘
```

**The role of each layer:**

- **UPT** owns the **physics knowledge base** — the 40 bridge equations as validated ASTs with dimensional bookkeeping, plus the algebra/metric/connection/curvature primitives. UPT is the source of truth for "is this equation well-formed and dimensionally consistent?"
- **mathjs** owns **numerical computation** — given a validated UPT AST plus numerical inputs, mathjs lowers tensor-products to `math.einsum` / `math.multiply`, evaluates expressions, solves the ODEs/PDEs that bridge equations imply.
- **threejs** owns **interactive visualization** — given a numerical simulation result from mathjs + the structural metadata from UPT (rank, free indices, variance), threejs renders tensor fields, evolution trajectories, parameter-sweep results.

**The TensorJS top-level API** ties them together:

```typescript
// Sketch — not v0.2.0 work, but the surface UPT must support
const sim = await tensorjs.simulate({
  bridge: BRIDGE_EQUATIONS.find(b => b.id === 17),  // UPT catalog entry
  inputs: { /* numerical inputs */ },               // typed against UPT's Inputs interface
  solver: 'rk4',                                    // mathjs ODE solver
  visualization: { type: '6d-slice', axes: ['μ', 'ν'] }  // threejs config
});
```

### Architectural gaps surfaced by adversarial review

*(Recorded for visibility; resolved at TensorJS-bootstrap time, NOT v0.2.0. These do not block v0.2.0 implementation.)*

1. **The fourth layer: formulation / coordinate-mapping / discretization.** Going from a symbolic tensor equation (Einstein Field Equations) to a discretized PDE system for a numerical solver (BSSN formalism) is a multi-month domain-specific transformation that neither UPT nor mathjs nor threejs owns. TensorJS will need a formal "formulation strategy" layer that takes a UPT bridge equation + a chosen gauge + a coordinate system → produces a solver-ready PDE system. This is implicit in the `tensorjs.simulate({bridge, ...})` API sketch but unstated. **Acknowledge in v0.2.0 design; design at TensorJS bootstrap.**
2. **Initial / boundary conditions and grid spec are missing from the API sketch.** The `simulate({bridge, inputs})` shape over-promises by hiding IC/BC/grid as `inputs: {}`. Real-world simulations require complex IC functions, boundary specifications (periodic / fixed / outflow), domain definition, discretization scheme. A future `simulate()` API needs richer typed surface here. **Acknowledge in v0.2.0 design; design at TensorJS bootstrap.**
3. **mathjs lacks native einsum and high-performance numerical backend.** Implementing einsum on mathjs requires hand-rolled index parsing + contraction-path optimization (NP-hard in general) + transposition/reshape/multiply chain generation. mathjs is also pure-JS — for grid sizes typical in physics simulations (e.g., 64³ ≈ 260k points), pure-JS performance is bottlenecked. **v0.3.5 design must seriously evaluate TensorFlow.js (WebAssembly-backed) as the numerical backend, with mathjs as a development-mode fallback.**
4. **threejs visualization spec needs a declarative mapping layer.** "6D tensor slices" is not a technical spec. Real visualization requires a declarative mapping from tensor structure (rank, indices) to scene primitives (slicing, projection, glyphs, color channels). The TensorJS viz repo's first design milestone is this mapping spec, not the rendering implementation. **Acknowledge in v0.2.0 design; design at TensorJS viz-repo bootstrap.**
5. **Cross-layer error propagation needs coherent strategy.** UPT errors are typed; mathjs errors are generic; threejs failures are often silent. TensorJS must surface them as a unified error model. **Captured in §14.7 as a v0.2.0 forward-compat note (UPTError base class).**

### What this means for v0.2.0 implementation

The v0.2.0 scope **does not change** — algebra layer is still the right deliverable, and the API surface (`tsym`, `scale`, `contract`, enriched `ValidationResult`) is still the right shape. What changes is that **the v0.2.0 API surface is now a forward-load-bearing public contract**, not just internal UPT machinery. See §14 for the new forward-compat sanity checks the implementation must honor.

**The v0.2.0 design choice that most affects TensorJS readiness:** keeping the AST minimal (no type-level encoding) means future extensions add new node kinds without refactoring TypeScript types. Adding `metric`, `covariant-derivative`, or `riemann-tensor` is a discriminated-union addition, not a type-system refactor. mathjs/threejs integration is a downstream-consumer addition, not an UPT-internal refactor.

## 13. Risks and open questions

### Risks both reasoners flagged

- **Index label namespace ambiguity in nested expressions.** `(A^μ_ν B^ν_α) + C^μ_α` requires the validator to scope `ν` to within the parenthesis (it's a dummy local to the product). The recursive walker handles this naturally if implemented correctly, but it's a class of bug to watch for in week 4 of implementation.
- **The "uniform component dimension" assumption is leaky.** Faraday tensor `F_μν` has electric-field components and magnetic-field components with different SI dimensions in `[V/m]` vs `[T]`. v0.2.0 documents this as a known limitation; v0.3.0 may need a `per-pair-dim` extension to `tensor-symbol`.
- **Multi-pair contraction edge cases.** Expressions like `R^α_β R_α^β` (full self-contraction) need careful walker implementation to handle both pairs simultaneously. Gemini specifically flagged this when reviewing the `{ contract, t1, t2 }` shape; the chosen `{ tensor-product, args: [...] }` shape sidesteps it.

### Open questions — decision log

1. **`tensor-product` canonical ordering of free indices.** Status: **open**. Suggest deferring decision until first concrete bug emerges.
2. **`tensor-symbol` allows zero indices** (rank-0 tensor = scalar via tensor API). Status: **resolved — yes**. The validator's empty-`freeIndices` case handles this without special-casing.
3. **`contract(...)` / `scale(...)` argument-shape validation at API vs validator level.** Status: **open**. Suggest defer-to-validator for v0.2.0; reconsider after first ergonomic complaint.
4. **Partial-derivative AST node** *(surfaced by adversarial review, Gemini 2026-05-12)*. The roadmap jumps from algebra (v0.2.0) directly to covariant derivative (v0.4.0), but `∇_μ V^ν = ∂_μ V^ν + Γ^ν_μλ V^λ` is defined in terms of the partial derivative `∂_μ`, which has no AST node. Status: **resolved — spec preview only (user decision, 2026-05-12)**. Part-VII includes a "partial-derivative preview" section locking in the shape `{ kind: 'tensor-partial-derivative', wrtIndex: { label, variance: 'lower' }, of: ExprNode }`. No v0.2.0 runtime support. v0.3.0 implements against the locked spec.
5. **Independent vs dependent variables distinction** *(surfaced by adversarial review, Gemini)*. Status: **resolved — yes, add optional `role` field (user decision, 2026-05-12)**. `tensor-symbol` gains an optional `role: 'coordinate' | 'field' | 'constant'` field, defaulting to `'field'`. Backward-compatible for v0.2.0; forward-compatible for v0.3.0 partial-derivative work.
6. **Storage-order convention** *(surfaced by adversarial review)*. Status: **resolved — make explicit in Part-VII**. Indices `[μ, ν, λ]` map to numerical storage `M[μ_idx][ν_idx][λ_idx]` (leftmost = outermost dimension). Spec-level invariant; locks mathjs/TensorJS interop semantics from day one.
7. **`UPTError` base class** *(surfaced by §14.7 adversarial review)*. Status: **resolved — yes, refactor existing + new errors under common base (user decision, 2026-05-12)**. See §2.4 (in scope).

8. **Tensor-structural encoding scope for BE-33 / BE-36 / BE-43** *(surfaced
   by v0.2.0 Task 12, 2026-05-12)*. Original §2.7 scope proposed structural
   encoding of BE-17 plus "at least one of {BE-33, BE-36, BE-43}." Task 12
   discovered that **none of the three carry native tensor structure in
   their post-Wave-P canonical forms**: BE-33 reformulated to the
   Hertz-Millis scalar correlation length `ξ ~ T^(-ν/z)` (scalar — no
   indices); BE-36 reformulated to the GW170817 graviton-speed scalar
   ratio `|c_g − c|/c ≲ 10⁻¹⁵` (scalar — no indices); BE-43 reformulated
   to the Bekenstein-Hawking scalar entropy bound `S ~ A_wormhole / (4
   ℓ_P²)` (scalar — no indices). There is no tensor structure to encode.
   Status: **resolved — criterion #7 rewording**. Success criterion #7
   in §11 was updated to drop the "at least one of {BE-33, BE-36, BE-43}"
   wording; tensor-bridge expansion deferred to a future milestone when
   either (a) new tensor bridges enter the catalog, or (b) literature
   canonical forms with tensor structure surface for these three. BE-17
   remains the sole structurally-encoded bridge for v0.2.0 (per criterion
   #6, non-negotiable).

## 14. Forward-compatibility sanity checks (TensorJS-aware)

Because v0.2.0's API surface is now a **load-bearing public contract** for TensorJS (see §12), implementation must satisfy these checks before merging anything that touches the public surface:

### 14.1 `tensor-symbol` must lower cleanly to mathjs

A future mathjs backend will need to convert a UPT `tensor-symbol` into a numerical mathjs `Matrix` (or equivalent N-dimensional array). For this to be clean:

- The `indices` array's order **defines the storage order** of the eventual numerical tensor. Implementation must NOT reorder indices internally; users see them in declaration order.
- The `dim` field describes the **per-component physical dimension**; the mathjs `Matrix` carries numerical values; their product is the actual physical quantity. Implementation must keep `dim` and component-count strictly separate (no conflating).
- The variance information (`upper`/`lower`) is **structural metadata** mathjs doesn't natively model. UPT must preserve it as a parallel structure that the mathjs backend can read but not lose.

**Concrete sanity check during v0.2.0:** write one passing test that constructs a `tensor-symbol`, dumps it to a JSON-serializable shape, and verifies the shape is sufficient to reconstruct the equivalent mathjs `math.Matrix({...})` call. (Test is small; lives in `tests/dimensional/tensor-symbol-mathjs-shape.test.ts` or similar.)

### 14.2 `tensor-product` must lower cleanly to einsum-style contraction

A future mathjs backend will need to convert a UPT `tensor-product` into a numerical contraction. Mathjs's API for Einstein summation: `math.multiply` for plain tensor product, custom helper for index-aware contraction (mathjs does not yet expose a direct `einsum`).

For UPT's `tensor-product` to lower cleanly:

- The contraction logic in the validator (which pairs upper/lower indices) must be **exportable as a separate function**, not buried inside the recursive walker. Backend code can then reuse it to generate the einsum index pattern.
- A `tensor-product` node's `args` field is read-only; the validator's contraction decision is **deterministic** for a given args list. mathjs will replay the same contraction numerically; both must agree.

**Concrete sanity check during v0.2.0:** the `freeIndices`-tracking logic lives in a pure function `computeContraction(args: ExprNode[]): { dim, freeIndices, contractionPairs: Array<{label: string}> }` exported from the tensor module. The validator calls this function; future mathjs backend will too.

### 14.3 Bridge catalog must expose a stable API for downstream consumers

TensorJS will iterate the bridge catalog (`BRIDGE_EQUATIONS`) to discover available equations. For this to remain stable across v0.2.0 → v0.3.0 → TensorJS:

- The `BridgeEquation` interface in `src/bridges/index.ts` must not gain breaking changes during v0.2.0 polish work. Adding fields is fine; renaming or removing existing fields is breaking.
- Each bridge with a structural tensor encoding (BE-17, BE-33, BE-36, BE-43 post-v0.2.0) must expose its AST in a way downstream consumers can introspect (e.g., the LHS/RHS `ExprNode` is exported and stable).
- The dimensional analyzer's public functions (`validate`, `validateEquation`, `format`) must remain backward-compatible signatures throughout v0.2.0.

**Concrete sanity check during v0.2.0:** `tests/bridges/public-api-stability.test.ts` snapshots the shape of the `BRIDGE_EQUATIONS[0]` object and asserts every existing field remains. Adding fields to the snapshot is intentional; removing them fails the test.

### 14.4 ESM-friendly exports

mathjs and threejs are both ESM-friendly modern packages. UPT's exports must remain ESM-compatible (no implicit CommonJS reliance in the public surface). The v0.1.0 build uses ESM-output `tsc`; v0.2.0 must not regress this.

**Concrete sanity check during v0.2.0:** the existing build/test pipeline already enforces this; no new work required. Just don't add `require()` calls or CJS-only dependencies.

### 14.5 Versioning posture: SemVer is now load-bearing

Post-v0.1.0, the CHANGELOG header explicitly declares SemVer authoritative. With TensorJS as a downstream consumer:

- Breaking changes to the AST node types (`ExprNode` discriminated union) bump major: 0.x → 1.0 → 2.0.
- Adding new node kinds (e.g., adding `metric` in v0.3.0) is NOT breaking — it's an additive extension of a discriminated union; existing consumers ignore the new kind.
- Removing old typed-stubs from bridge modules (BE-17's `T_torsion_squared`) **is a breaking change**, full stop. Pre-1.0 (0.x) SemVer permits minor version bumps to include breaking changes, so v0.2.0 can ship the stub removals while staying SemVer-compliant. Each removal is documented as `### Changed` (with explicit "BREAKING:" prefix) in CHANGELOG and listed in a v0.2.0 migration note. This is not "judged safe because no consumer exists" (that mindset normalizes breakage); it is "SemVer-correct for pre-1.0 minors, with explicit migration documentation."

### 14.6 Round-trip consistency (AST → mathjs → reconstructed structural model)

*(Surfaced by adversarial review, OpenAI 2026-05-12.)*

When v0.3.0 adds the mathjs numerical backend, simulations should support round-tripping: a UPT AST is lowered to mathjs numerical structures; the numerical output, when re-interpreted through UPT's structural metadata, should reproduce the original AST shape (same rank, same free indices, same variance). This is the integration-test analog of "compile-then-decompile" yielding the same result.

**Concrete sanity check for v0.2.0:** the AST → JSON serialization (already implied by §14.1) must include enough metadata that JSON → AST reconstruction is lossless. Test: serialize the BE-17 RHS to JSON, parse it back, assert structural equality. Lives in `tests/dimensional/tensor-ast-serialization.test.ts`. Catches subtle issues where the AST stores derived data that doesn't survive serialization.

### 14.7 Cross-layer error propagation

*(Surfaced by adversarial review, OpenAI 2026-05-12.)*

UPT, mathjs, and threejs each generate their own error types. TensorJS must surface them coherently to the user. The design constraints:

- **UPT errors** are typed (`DimensionMismatchError`, `IndexLabelCollisionError`, etc.) with `expected` / `actual` / `note` shapes. They propagate up cleanly through the validator's recursive walker.
- **mathjs errors** are mostly `Error` instances with string messages. They lose typing information at the JS exception layer.
- **threejs errors** are typically silent rendering failures or WebGL context losses. Not exception-shaped.

**Forward-compat note for v0.2.0:** UPT error types should be **subclassed from a common base** (suggest `UPTError extends Error`) so mathjs/threejs integrations can `instanceof UPTError` to distinguish UPT-source errors from generic Error. Suggest applying this to the existing `DimensionMismatchError` plus all new v0.2.0 error types (`IndexLabelCollisionError`, etc.). Small refactor; large interop payoff. **Add to v0.2.0 implementation scope.**

### 14.8 Independent-variable / coordinate distinction

*(Cross-referenced from §13 open question #5.)*

If adopted in v0.2.0, the optional `role: 'coordinate' | 'field' | 'constant'` field on `tensor-symbol` becomes a forward-compat constraint: every consumer that introspects `tensor-symbol` must tolerate `role` being absent (v0.1.0 had no such field; v0.2.0 makes it optional, defaulting to `'field'`). Set explicitly when authoring; defaulted when reading legacy. Document in Part-VII spec; lock as forward-compat invariant.
