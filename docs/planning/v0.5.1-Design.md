## Architectural Decisions (locked)

### Decision #1 — Constants canonicalization shape

**Decision**: Introduce `src/core/constants.ts` with **flat named exports** (`C_SI`, `G_SI`, `HBAR_SI`, `H_SI`, `K_B_SI`, `M_P_SI`, `T_P_SI`, `L_P_SI`, `E_SI`, `ALPHA`, `H0_SI`), **not** an extension of the `PhysicalConstants` namespace.

**Rationale**: The flat-export pattern matches v0.5.0 ergonomics (`{ christoffel, ricci, einstein, bianchiResidual }` from `core/curvature`; `{ GL4_C, GL4_A, GL4_B }` from `numerical/gl4-integrator`). Per Adam+Eve audit vet (Eve's PC-4 challenge) the existing `PhysicalConstants` namespace in `src/core/types.ts:173-200` is **dead public API** (never imported); migrating to flat exports rather than evangelizing the namespace minimizes refactor surface in consumer code.

**Alternative considered**: Re-export `PhysicalConstants` via `src/index.ts` and have callers do `PhysicalConstants.c`. Rejected: longer call sites, `PhysicalConstants.c` reads as instance-access (it's a frozen namespace), and the v0.4.6 audit similarly preferred flat-export ergonomics.

**Migration path**: `PhysicalConstants` stays exported for v0.5.1 (no break); v0.6.0+ may deprecate. v0.5.1 wires every internal call site to the new flat exports.

### Decision #2 — `pderiv.ts` 4th-order stencil ergonomics

**Decision**: Add an **optional `order` parameter** (`order?: 2 | 4 = 2`) to `pderivNumericalFn` and `pderivGrid`, preserving v0.4.0 2nd-order default behavior. Consumers explicitly opt in to 4th-order via `{ order: 4 }`.

**Rationale**: Adam pushed for an unconditional `pderiv.ts` upgrade (his finding #3, reinforcing PD-7). I reject the unconditional upgrade — it changes the precision floor for every v0.4.0 consumer (covariant-derivative lowering, BE-37 eikonal, geodesic Christoffel evals), some of which are calibrated against the 2nd-order tolerance band. Opt-in is the conservative middle path: callers that hit SI-c² cancellation upgrade their site; callers that don't aren't perturbed.

**Migration**: `curvature-lowering-helpers.ts` (the v0.5.0 site already using 4th-order) refactors to pass `{ order: 4 }` to the shared `pderiv` rather than reimplementing the stencil. Net LOC reduction; behavior preserved.

### Decision #3 — `scanForMetricPair` extension shape

**Decision**: Extend the existing `walk` function in `src/numerical/metric-inverse.ts:73-83` with case arms for the 5 curvature node kinds: `covariant-derivative`, `riemann-tensor`, `ricci-tensor`, `einstein-tensor`, `bianchi-residual`. Each case walks the relevant metric sub-references.

**Rationale**: Minimal-surface fix. Adam upgraded PC-3 to HIGH and the reasoning is "a validation mechanism that doesn't run is worse than no validation at all". The fix is a 5-case `switch` extension, ~20 LOC, no API change.

**Alternative considered**: Refactor `scanForMetricPair` to walk via a visitor pattern dispatched off `ExprNode`'s discriminated union. Rejected: bigger refactor for marginal benefit; opens the door to future "forgot to update the visitor" bugs identical to the one PC-3 documents.

### Decision #4 — `connection-validators.ts` test coverage scope

**Decision**: Add `tests/dimensional/connection-validators.test.ts` with **per-throw-path unit tests** for `validateCovariantDerivative` and `validateRiemannTensor`. Mirror the v0.5.0 `tests/dimensional/riemann-tensor.test.ts` test-naming pattern.

**Rationale**: UC-1 is the highest-priority test-coverage gap. Per-throw coverage on this critical-path validator catches the kind of bugs that v0.5.0's Riemann-formula-and-Ricci-slot debacle exposed (validators silently accepting wrong inputs). v0.4.6's pattern of "per-function unit coverage on the validator layer" is the precedent.

**Test inventory** (minimum):
- `validateCovariantDerivative`: 4 throw paths (`wrtIndex.variance !== 'lower'`, `gLower` not both-lower, `gInverse` not both-upper, `wrt` label collision) + happy path.
- `validateRiemannTensor`: 5 throw paths (`upperIndex.variance !== 'upper'`, `lowerIndices.length !== 3`, gLower signature, gInverse signature, label collision) + happy path.
- Total: ~10 `it(...)` blocks.

### Decision #5 — Flat-Minkowski curvature test placement

**Decision**: Create `tests/dimensional/minkowski-curvature.test.ts` covering Riemann/Ricci/Einstein/Bianchi lowering on the trivial Minkowski metric `g_μν = diag(-1, 1, 1, 1)·c²` (mostly-plus SI convention matching v0.5.0 Schwarzschild fixture). All curvature components must be zero to machine precision.

**Rationale**: Adam's flat-Minkowski test gap (NEW-1, HIGH post-vet) is a real physics edge case. Minkowski is the universal "everything goes to zero" sanity check. If the curvature lowering pipeline returns non-zero on flat spacetime, every subsequent Schwarzschild test result is suspect.

**Tolerance**: `|R^ρ_{σμν}| / scale_local < 1e-12` (machine-epsilon range — flat space has no FD cancellation noise since `g^μν` is constant).

### Decision #6 — `bianchiResidual()` type-tightening via `import type`

**Decision**: Break the `dimensional/` → `numerical/` runtime cycle in `bianchiResidual()` (currently dynamic-imported per call, with `any`-typed engine/inputs) by switching to `import type { TensorEngine, NumericalInputs, NestedArray }` from `../numerical/*`. Type imports are erased at compile time so they introduce no runtime cycle. Replace the 6 `any` annotations + the dynamic `import('../numerical/index.js')` with a hoisted static import.

**Rationale**: TS-1 (HIGH) + AS-4 (MEDIUM) collapse into one fix. The cycle-avoidance pattern the owner originally chose is correct in spirit (no runtime cycle) but unnecessarily reaches for `any` and per-call dynamic import.

**Verification**: `tsc --noEmit` must still pass post-change. If TypeScript surfaces a real circular import (it shouldn't — types are erased), fall back to keeping the dynamic import but typing it via `import type` only.

### Decision #7 — `it.todo` zombie removal scope

**Decision**: Delete all 7 zombie `it.todo` markers identified in PD-9 / UC-5 / AS-5 (they're three audit IDs for the same set). Replace nothing — the milestones they refer to have all shipped and have real tests elsewhere. Keep the single legitimate `it.todo` in `tests/bridges/catalog-integrity.test.ts:137` (BE-42 geodesic intentional deferral — Hawking temperature has no geodesic content).

**Rationale**: Zombie markers carry "pending" semantics in vitest reporters and mask actual coverage gaps. The Pareto-clean fix is removal, not replacement.

### Decision #8 — Bench harness for NEW-2 (GL4 alloc) before opt

**Decision**: Add `bench/gl4-picard-alloc.bench.ts` measuring Picard inner-loop wall-time on a representative Mercury orbit segment **before** attempting the buffer-reuse optimization Adam proposed.

**Rationale**: Adam's GL4 hot-loop allocation finding is SUSPECTED (he flagged it as "likely"). The audit's NEW-2 is properly marked SUSPECTED — bench-required. If the benchmark shows allocation cost is <2% of wall-time, the optimization is premature (Karpathy's "measure before optimize" rule from `karpathy-guidelines` skill).

**Trigger threshold**: Implement buffer reuse only if bench shows allocation >5% of step wall-time, or >10% GC-attribution under Node's `--trace-gc`.

### Decision #9 — `--ignore-scripts` framing

**Decision**: **Won't fix.** Add a note to `CLAUDE.md` and `README.md` documenting the deliberate `npm publish --ignore-scripts --access public` pattern (vitest cold-start avoidance on Windows; suite is already verified at release gate).

**Rationale**: Adam flagged this as a release-hygiene concern. The pattern is intentional per CLAUDE.md / todo.md `§Conventions`. Documenting it more visibly in README is the right call; "fixing" it (re-enabling scripts) would re-introduce the 3-5 min Windows cold-start that triggered the workaround in v0.4.5.
