### UC-1 — `lowering.ts` line 471-472: partial computed unconditionally but the comment is the only thing explaining why — and the comment is wrong (MEDIUM)

**File**: `src/numerical/lowering.ts`, lines 462-493

**Finding**: The block comment at line 470 says:
> "(partial is also needed by the 'supplied' path below, so we compute it unconditionally and use the early return only for 'computed'.)"

This is CORRECT logic — but the code structure implies `partial` is computed before the `strategy === 'zero'` early-return check. Read the actual flow:

1. Line 457: `if (strategy === 'zero') { return zeroTensor(...); }` — early return for `'zero'`
2. Lines 473-486: `partial` is computed (unconditionally at this point)
3. Line 491: `if (strategy === 'computed') { return partial; }` — early return for `'computed'`
4. Lines 500-502: `if (ofFreeIndices.length === 0) { return partial; }` — early return if scalar operand

**The actually unreachable case**: after the `strategy === 'zero'` and `strategy === 'computed'` early returns, `strategy` at line 518 can ONLY be `'supplied'`. This is a **dead type arm in the cast**, not a runtime error, but it creates a misleading type at the `getMetricDerivFlat` call site.

**Fix**: Change line 518 from `strategy as 'zero' | 'supplied'` to `'supplied'` (literal, no cast needed). This is the only value that can reach that line.

**Severity**: MEDIUM — the cast works at runtime (the `'zero'` branch of `getMetricDerivFlat` just returns zeros and is never reached), but it misrepresents what the code can actually do.

### UC-2 — `lowering.ts` lines 482-486: `else` branch in partial-computation block is dead (HIGH)

**File**: `src/numerical/lowering.ts`, lines 474-486

**Finding**: The code computing `partial`:
```ts
if (ofExpr.kind === 'tensor-symbol' || ofExpr.kind === 'metric-tensor') {

  // Scalar or other: partial derivative is zero.

The `of` field in a covariant-derivative node is, per the v0.4.0 design, always a tensor-symbol or metric-tensor (any other `of` would have failed dimensional validation before reaching the lowering phase — the validator walk in `validator.ts` line 554-555 throws for unknown kinds, and partial-derivative child resolution only accepts tensor-symbol, metric-tensor, kronecker-delta, and tensor-partial-derivative). **Proof by elimination**: the `case 'covariant-derivative'` arm begins only after `validate(node)` passes (see `evaluateNumerical` in `index.ts` line 80). A validated covariant-derivative with `of.kind !== 'tensor-symbol' && of.kind !== 'metric-tensor'` would be a covariant-derivative of a scalar, where `ofFreeIndices.length === 0`, which exits at line 500-502. The `else` branch below line 482 can never fire.

**Fix**: Remove the `else` branch (lines 482-486). Replace with an assertion:
```ts

Or restructure the if/else to throw: `throw new NumericalBackendError('unreachable: covariant-derivative of must be tensor-symbol or metric-tensor')`.

**Severity**: HIGH — dead code that conceals the actual invariant. Removing it makes the constraint explicit.

### UC-3 — `tensor.ts` lines 213-215: `Array.from(merged.entries())` copies before deleting (MEDIUM)

**File**: `src/dimensional/tensor.ts`, lines 213-215

**Finding**:
```ts
for (const [label, counts] of Array.from(merged.entries())) {
  if (counts.upper === 0 && counts.lower === 0) merged.delete(label);
}
```

The `Array.from(merged.entries())` snapshot is taken to allow mutation during iteration. However, in Step B (lines 191-208), when a label is fully contracted (`pairs === counts.upper === counts.lower`), `merged.set(label, { upper: 0, lower: 0 })` is called. Labels that are NOT contracted still have non-zero counts. Labels that ARE contracted have counts set to `{ upper: 0, lower: 0 }`.

This means Step C will always delete exactly the labels that Step B set to zeros — so Step C is equivalent to just deleting all labels whose final count is `{upper: 0, lower: 0}`. The snapshot is NOT needed for correctness here because we are iterating and deleting, not modifying counts. You CAN delete from a Map during `for...of` iteration over a freshly obtained entries view in modern JS, but the `Array.from` snapshot is needed to avoid the iterator-invalidation issue.

VERDICT: The `Array.from` is correct but it allocates an unnecessary array. This belongs under **Category 4** (algorithmic simplification). See AS-5 below.

**Severity**: LOW — not unreachable, moved to algorithmic category.

### TS-1 — `mathts-engine.ts` lines 119, 132, 159, 171: `as any` casts for the optional autograd dep (HIGH)

**File**: `src/numerical/mathts-engine.ts`

**Locations**:
- Line 119: `let autograd: any;` (used in forwardGrad)
- Line 132: `await autograd.forwardGrad(fn as any, xMathts as any)`
- Line 159: `let autograd: any;` (used in reverseGrad)

**Severity**: HIGH — `any` casts suppress type-checking at the boundary where the optional dep's API is consumed. A breaking change in mathts-autograd would produce runtime errors with no compile-time signal.

### TS-3 — `float64-engine.ts` lines 391-429: AD dispatch via duck-typing `'tangent' in a` and `'tape' in a` — fragile property-existence checks (HIGH)

**Severity**: MEDIUM — warning-severity violations from the probe exponent are silently discarded. In practice, `'^'` exponents are simple numeric symbols so this is low-risk, but the pattern is subtly wrong.

## Category 4: Algorithmic Simplifications

### AS-1 — THREE independent `flattenNestedArray` implementations in the numerical module (HIGH)

**Files**:
1. `src/numerical/connection-lowering-helpers.ts` line 31: `flattenNA(data: NestedArray): number[]`
2. `src/numerical/lowering.ts` line 92: `flattenNestedArray(data, expectedSize)` (wrapper over flattenNA)
3. `src/numerical/pderiv.ts` line 15: `flattenToNumbers(data: NestedArray): number[]`

**Finding**: `flattenToNumbers` in `pderiv.ts` is a LOCAL private function that is functionally identical to `flattenNA` in `connection-lowering-helpers.ts`. Both recursively walk a `NestedArray` and collect numbers in row-major order. Neither is exported from `pderiv.ts`.

`pderiv.ts` could simply import `flattenNA` from `connection-lowering-helpers.ts` and delete `flattenToNumbers`. This eliminates one of three implementations.

**Proof of equivalence**:
- `flattenNA`: `if (typeof data === 'number') return [data]; const out = []; walk(data); return out;`
- `flattenToNumbers`: `if (typeof data === 'number') return [data]; const out = []; walk(data); return out;`
Same algorithm, different name.

**Fix**: In `pderiv.ts`, remove `flattenToNumbers` (lines 15-24). Import `flattenNA` from `'./connection-lowering-helpers.js'`. Replace 3 usages at lines 43, 88, 89 with `flattenNA`.

**Severity**: HIGH — duplicate function with no distinguishing behavior. Maintaining two copies risks divergence.

### AS-4 — `connection-lowering-helpers.ts` lines 257-290: `forEachMultiIndex` allocates a fresh `number[]` on every `visit` call via `[...idx]` (MEDIUM)

**File**: `src/numerical/connection-lowering-helpers.ts`, lines 264, 319-328

**Finding**: `forEachMultiIndex` calls `visit([...idx])` at line 264 — spreading the `idx` array on every iteration. For a 4D Christoffel computation this is called N^4 = 256 times (N=4). Each spread allocates a new array.

Compare to `float64-engine.ts`'s `forEachIndex` which calls `visit(idx)` at line 359 — passing the SAME array reference to the visitor. The `float64-engine.ts` version is more efficient (visitor must not mutate), and the visitor pattern there does NOT mutate the idx.

The `contractChristoffelWithOperand` visitor at line 264 does not mutate `outIdx` (it calls `outIdx.slice(0, rank)` and `tIdx[freeIdxPos] = lam` on the SLICE, not on outIdx). So the spread in `forEachMultiIndex` is unnecessary.

**Fix**: Change `visit([...idx])` to `visit(idx)` in `forEachMultiIndex`. Add a comment: "Visitor must not mutate the passed idx array." The visitor in `contractChristoffelWithOperand` uses `.slice()` already, so it is safe.

**Severity**: MEDIUM — eliminates N^4 array allocations per Christoffel contraction. In N=4 spacetime: 256 avoided allocations per covariant-derivative lowering call.

### AS-5 — `tensor.ts` lines 213-215: `Array.from(merged.entries())` for safe Map iteration during deletion (LOW)

**File**: `src/dimensional/tensor.ts`, lines 213-215

**Finding**:
```ts
for (const [label, counts] of Array.from(merged.entries())) {
  if (counts.upper === 0 && counts.lower === 0) merged.delete(label);
}
```

The `Array.from` snapshot is taken because you cannot delete from a Map while iterating its `entries()`. However, an alternative is to collect the keys to delete first, then delete in a separate loop — avoiding the full entries array allocation:

```ts
const toDelete: string[] = [];
for (const [label, counts] of merged) {
  if (counts.upper === 0 && counts.lower === 0) toDelete.push(label);
}
for (const label of toDelete) merged.delete(label);
```

This avoids allocating the full entries tuple array (just a string array of deleted keys, which is typically small — only contracted labels).

**Severity**: LOW — minor allocation optimization in a function called per validated tensor-product. In typical bridge equations with 2-4 contractions, this is not a bottleneck.

### AS-6 — `geodesic-integrator.ts` lines 122-132: inner RK4 loop recomputes `G = christoffelFn(x)` at each of 4 stages with a fully nested array return (MEDIUM)

**File**: `src/numerical/geodesic-integrator.ts`, lines 113-132

**Finding**: `geodesicRHS` is called 4 times per RK4 step. Each call invokes `christoffelFn(x)` which must return a `readonly (readonly (readonly number[])[])[]` — a fully nested 4x4x4 array structure. The inner triple-loop then accesses `G[mu][nu][rho]`.

For a flat array representation, each `G[mu]` and `G[mu][nu]` lookup follows object references through two levels of array indirection. This is 64 nested-array accesses per `geodesicRHS` call, 256 per RK4 step.

**However**: This is an algorithmic interface concern — changing the `christoffelFn` signature to accept a flat `[64]` array would be a breaking API change. VERDICT: Cannot simplify without breaking the public interface. Do NOT flag for v0.4.6.

**Revised Severity**: LOW — noted but out of scope for v0.4.6 without a breaking change. Deferred to v0.5.0 API review.

### AS-7 — `float64-engine.ts` lines 562-586: `operandFlatIndex` closure re-walks `spec.free` and `spec.contractions` on every element (MEDIUM)

**File**: `src/numerical/float64-engine.ts`, lines 562-584

**Finding**: The `operandFlatIndex` closure at line 562 is called once per output element per operand. It iterates `spec.free` and `spec.contractions` to set `idx` entries. For a 4x4 contraction with 2 operands and 3 free axes, this closure is called 64 × 2 = 128 times, each iterating the spec arrays.

// freeAxesByOp[o] = array of {varIdx, axis} pairs

Then inside `operandFlatIndex`, iterate the precomputed small arrays instead of the spec.

**Severity**: MEDIUM — reduces iteration cost inside the innermost loop of the einsum. For 4D spacetime tensor contractions, the improvement could be 2-5x for medium-rank tensors.

### AS-8 — `connection-lowering-helpers.ts` lines 162-185: `getMetricDeriv(mu)` is called 3 times per (mu, nu) pair in Christoffel computation, fetching the same `dmu`/`dnu` arrays repeatedly (MEDIUM)

**File**: `src/numerical/connection-lowering-helpers.ts`, lines 162-184

**Finding**: The Christoffel computation loops over `(alpha, mu, nu, rho)`. Inside the `rho` loop:
```ts
const dmu = getMetricDeriv(mu);  // called once per (alpha,mu,nu) iteration
const dnu = getMetricDeriv(nu);  // called once per (alpha,mu,nu) iteration
for (let rho = 0; rho < N; rho++) {
  const drho = getMetricDeriv(rho);  // called N times per (alpha,mu,nu) iteration
```

For strategy='supplied', `getMetricDerivFlat` calls `flattenNA` on the stored `NestedArray` each time. For N=4: `dmu` and `dnu` are computed once per (alpha,mu,nu) triple — that is N^3 = 64 times each. `drho` is computed N^4 = 256 times total (N per (alpha,mu,nu) combo).

**But**: `dmu` and `dnu` are already hoisted OUT of the rho loop (they are at the mu/nu level). Only `drho` = `getMetricDeriv(rho)` is inside the rho loop and is called N^3 times. Hoisting `drho` outside the alpha loop (precompute `dgrid[mu]` for all mu before the alpha loop) would reduce from N^3 calls to N calls.

**Fix**: Precompute all N metric derivative arrays before the triple loop:
```ts
const dMetric = Array.from({ length: N }, (_, mu) => getMetricDeriv(mu));
```
Then replace `getMetricDeriv(mu)`, `getMetricDeriv(nu)`, `getMetricDeriv(rho)` with `dMetric[mu]`, `dMetric[nu]`, `dMetric[rho]`.

For strategy='supplied', this reduces `flattenNA` calls from N^2 + N^2 + N^3 to N total.

**Severity**: MEDIUM — for N=4 with 'supplied' strategy: reduces from ~96 `flattenNA` calls to 4. The function's O(N^4) behavior remains but the constant factor shrinks.
